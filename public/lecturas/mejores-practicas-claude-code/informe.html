Cómo configurar Claude Code solo donde importa

Con un prompt sencillo, Claude Code ya hace lo correcto casi siempre. La configuración sirve para lo que no puede ver, comprobar ni evitar por sí solo: cuéntale lo que no está en el repo, dale un chequeo que pase o falle, haz cumplir por configuración lo que no admite excepciones y cambia un valor por defecto solo cuando cuesta de más.

El punto de partida

Con un prompt sencillo, Claude Code ya hace lo correcto casi siempre

Los valores por defecto ya resuelven mucho: las sesiones nuevas de terminal y VS Code arrancan en modo auto, así que los comandos corren sin que apruebes cada uno; Claude delega trabajo independiente en subagentes; y la conversación se compacta sola antes de llenar la ventana de contexto.

La guía trata de lo que hacer cuando eso no basta, y siempre se debe a lo mismo: el proyecto tiene algo que Claude no ve desde el código. Un proceso de deploy que vive en la cabeza de alguien, un archivo que nunca debe leerse, un chequeo que debe pasar, un presupuesto que no se puede superar. Cuando una sesión no sale como esperabas, casi siempre es una de cuatro causas, y cada una tiene su remedio.

ImplicaciónAntes de configurar nada, identifica cuál de las cuatro causas tienes. Casi nunca hace falta tocar las cuatro.

Dos tipos de instrucción

Hay instrucciones que Claude decide y otras que Claude Code obliga

Toda instrucción es de uno de dos tipos. En las no deterministas la escribes tú y la lee el modelo: tu prompt, el CLAUDE.md o una skill. Casi siempre la sigue, pero no hay garantía. En las deterministas la configuras tú y la ejecuta el propio Claude Code, sin importar lo que decida el modelo: un hook, una regla deny o un ajuste gestionado.

Casi todo existe en las dos versiones. Casi siempre conviene que decida Claude, porque con el código delante suele juzgar mejor que una regla escrita de antemano. Lo determinista es para lo que debe pasar siempre, o nunca, sea cual sea la decisión del modelo.

ImplicaciónSi subes el énfasis de una línea de CLAUDE.md y Claude sigue saltándosela, esa línea es un hook. Y si tienes hooks para meras preferencias, bórralos y deja que Claude decida.

Lo que no puede ver

Escribe solo lo que Claude no puede encontrar leyendo el repo

Claude empieza cada tarea leyendo tu código, y los modelos actuales lo hacen muy bien: encuentran la estructura de archivos, las convenciones, el framework de pruebas y cómo se construyen los componentes, a menudo más rápido de lo que tú lo explicarías. Lo que no pueden encontrar es lo que nunca estuvo en el repo: una decisión tomada en una reunión, un proceso de deploy que vive en la cabeza de una persona, la variable de entorno que necesitan las pruebas de integración.

Hay además información que sí está en el repo pero cuesta minutos de búsqueda, y Claude repite esa búsqueda al inicio de cada sesión. Antes de escribir algo para Claude, la guía propone una prueba de dos preguntas.

El mismo criterio vale para el prompt: un prompt específico da la información que Claude no tiene. En lugar de «arregla el bug de login», la guía propone algo como «los usuarios reportan que el login falla tras expirar la sesión; mira el refresco de token en src/auth/, escribe una prueba que lo reproduzca y luego arréglalo». Si ya tienes lo que Claude necesita, entrégalo: un archivo con @ruta, una captura pegada o la salida de un comando por tubería.

Si todavía no sabes qué quieres, no hace falta decidirlo antes: pídele que te entreviste hasta poder escribir la especificación en SPEC.md y construye desde una sesión nueva. Y cuando quieras la versión completa de algo, dilo: be ambitious es una de las pocas frases que aún ayudan, porque informa del alcance que solo tú conoces.

ImplicaciónCada línea que escribes cuesta atención en todas las tareas. Si Claude puede encontrarlo y lo buscaría, es ruido.

Dónde ponerlo

Cada cosa va donde pesa menos: CLAUDE.md corto, reglas por zona, skills bajo demanda

El CLAUDE.md se carga en todas las sesiones, así que cada línea gasta un poco de atención en cada tarea, sea relevante o no. Por eso solo debe contener lo que Claude no puede deducir del código: cómo confirmar el trabajo (los comandos exactos de test, typecheck y lint), los lugares donde el código engaña, las decisiones que no están en el repo y cualquier cosa que ya hayas tenido que corregir dos veces.

Un CLAUDE.md que pasa la prueba se mantiene corto. No hace falta escribirlo desde cero: /init genera una versión inicial y el trabajo es sobre todo quitar líneas, /doctor sugiere recortes de lo que Claude ya deduce del código, y /doctor prompt-audit detecta instrucciones pensadas para modelos antiguos, que apuntan a archivos inexistentes o que se contradicen. Las preferencias personales van en CLAUDE.local.md, fuera del control de versiones.

CLAUDE.mdcorto
# Commands
- Install: pnpm install
- Run one test file: pnpm vitest run path/to/file.test.ts
- Typecheck: pnpm tsc --noEmit

# Conventions
- Use the error helpers in src/lib/errors.ts, never throw raw strings
- src/legacy/ is still live but don't copy its patterns into new code

# Gotchas
- Integration tests need DATABASE_URL set, see .env.example

Para lo que tiene efectos, como cortar un release, la guía añade disable-model-invocation: true a la skill: Claude no puede lanzarla por su cuenta y solo corre cuando tú escribes /release.

ImplicaciónUna skill larga no pesa sobre una tarea que no la usa; la misma explicación en CLAUDE.md sí.

Un chequeo que pase o falle

Si Claude puede comprobar su trabajo con un pasa o falla, deja de depender de ti

Claude se detiene cuando el trabajo parece terminado. Si no tiene nada que correr que le diga si de verdad lo está, «parece terminado» es todo lo que tiene, y entonces tú eres la suite de pruebas: cada error se queda ahí hasta que lo notes. Con un chequeo que devuelva pasa o falla, Claude cierra el ciclo solo: hace el cambio, corre el chequeo y, si algo se rompió, lee la salida y lo arregla antes de volver a correrlo.

El chequeo puede ser casi cualquier cosa con un resultado legible: un archivo de pruebas, el código de salida de un build, un linter, un script que compara una salida con un ejemplo guardado, o una captura del navegador junto al diseño. Si tu repo ya tiene uno, la línea más útil de tu CLAUDE.md es el comando que lo corre. Y se puede endurecer en pasos, de que decida Claude a que obligue Claude Code.

Pidas lo que pidas, exige evidencia: el comando que corrió y su salida, o la captura. «Todos los tests pasan» a secas dice muy poco, y para una sesión que no viste es la única prueba que tienes. Si el chequeo es una revisión contra tu plan, escribe tú el prompt y no quites la frase «skip style»: un revisor al que se le pide encontrar problemas siempre encontrará algo, y si arreglas todo acabas con capas de abstracción y pruebas para casos imposibles.

El hook Stop de la guía son pocas líneas en .claude/settings.json. El código de salida 2 es lo que impide parar, y lo que el comando imprima por stderr vuelve a Claude como la razón por la que no puede terminar. Si el hook bloquea ocho paradas seguidas sin ninguna llamada a herramienta entre ellas, Claude Code anula el siguiente bloqueo y cierra el turno.

.claude/settings.jsonhook Stop
{
  "hooks": {
    "Stop": [{
      "hooks": [
        { "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" }
      ]
    }]
  }
}

ImplicaciónUn chequeo vale más que cualquier instrucción de «sé cuidadosa»: convierte «parece terminado» en «está comprobado».

Reglas sin excepciones

Lo que nunca puede fallar va en un hook o una regla deny, no en CLAUDE.md

Reglas como «nunca leas .env», «siempre pasa el formateador al editar» o «no toques la carpeta de migraciones» Claude las seguirá casi siempre. Para las pocas donde «casi» no basta, sácalas de CLAUDE.md y llévalas a configuración que aplica el propio Claude Code. Desde ahí el resultado ya no depende de lo que el modelo recuerde o decida.

Los hooks ejecutan algo tuyo en puntos fijos del ciclo de Claude: antes o después de una herramienta, al intentar parar, al iniciar la sesión. Para una aplicación real usa hooks de tipo command o http; los de tipo prompt o agent piden a otro modelo que decida, así que tampoco son deterministas. Un hook es para una regla con cero excepciones: «prefiere exports con nombre» tiene muchas, y se queda en CLAUDE.md.

Las reglas deny deciden qué puede ejecutar, leer o traer Claude, y rigen en todos los modos, incluidos auto y bypassPermissions. Conocer sus bordes importa: la regla de lectura sí atrapa cat .env, pero no un script que abra el archivo, y una regla deny de WebFetch para un dominio no impide un curl al mismo, salvo que el sandbox esté activo. Para un límite a nivel de sistema operativo, /sandbox confina los comandos de shell y recoge esas reglas. Y el modo auto es un clasificador, no una regla dura: tus «nunca» van en reglas deny o hooks.

ImplicaciónMantén pequeño el conjunto que se hace cumplir: cada hook y cada regla deny saltará alguna vez cuando no debía y alguien tiene que mantenerlos. Si llegas a cuarenta, casi todos serán preferencias que Claude podía sopesar.

Permisos y esfuerzo

Cambia un valor por defecto solo cuando una tarea cuesta más de lo que vale

Los valores por defecto son suficientes hasta que una tarea cuesta más tiempo, tokens o interrupciones de los que debería. Entonces /usage muestra dónde se fue. Cuando pasa, casi siempre es uno de cuatro: el modo de permisos, el esfuerzo del modelo, los subagentes o el contexto.

En permisos, los dos extremos cuestan. En modo manual apruebas tú cada edición y cada comando, y tras el décimo empiezas a aprobar sin leer. Con bypassPermissions se aprueba todo lo que tus reglas no cubren, algo razonable solo en un contenedor desechable. El modo auto queda en medio: un clasificador revisa cada acción y se concentra en lo que querrías que frenara una persona. Si frena algo rutinario en tu entorno, descríbelo en la configuración del modo auto en lugar de aprobarlo a mano cada vez.

El esfuerzo es el control principal de cuánto piensa Claude y reemplaza casi todo lo que antes se hacía con el texto del prompt. Se cambia con /effort, y si solo una pregunta de la sesión lo necesita, basta con escribir ultrathink en ese mensaje.

ImplicaciónBaja el esfuerzo cuando vas rápido y revisas cada paso, súbelo cuando un error sería fácil de pasar por alto, y no pagues max por rutina.

Subagentes y contexto

Los subagentes dan paralelismo y ojos nuevos, no una respuesta más lista

Claude delega solo: las búsquedas amplias van al agente Explore, las tareas laterales se bifurcan y lo que arranca corre en segundo plano. Rara vez tienes que pedirlo, pero conviene saber qué recibes y qué cuesta. Un subagente no mejora la respuesta a la misma tarea: usa el mismo modelo, o uno menor, sobre el mismo problema.

La guía da una receta concreta para un revisor que no puede editar nada: un subagente en .claude/agents/reviewer.md con tools: Read, Grep, Glob y la instrucción de comparar los archivos con la especificación e informar solo de huecos de corrección. Esa limitación la aplica Claude Code, no se pide en un prompt.

El otro costo es el contexto. Con ventanas de 1M de tokens rara vez te quedarás sin espacio, pero sí puedes pagar por contexto que no necesitas: cada petición reenvía toda la conversación, así que una sesión con tres tareas distintas las relee en cada turno de la cuarta. Eso sale más barato mientras la caché está caliente y a precio completo cuando caduca (alrededor de una hora en suscripción y cinco minutos con clave de API).

ImplicaciónLimpiar entre tareas no relacionadas es gratis y evita pagar por el historial de la anterior. Vigila además lo que sigue enviando peticiones mientras no escribes: un /loop, la revisión de un goal tras cada turno y los subagentes.

Dirigir la sesión

Observa el primer minuto y, tras dos correcciones fallidas, empieza de cero

Ninguna configuración reemplaza mirar el primer minuto e intervenir cuando Claude va hacia donde no querías. Hay tres controles que vale la pena saberse de memoria: Esc detiene a Claude en plena acción conservando todo lo hecho; /rewind (o Esc dos veces con el prompt vacío) devuelve el código, la conversación o ambos a un punto anterior, así que es poco arriesgado probar primero el enfoque más atrevido; y /clear empieza de nuevo.

Los puntos de control cubren los archivos que Claude editó con sus propias herramientas en la conversación principal; un archivo que solo tocó un comando de Bash no se restaura, y funcionan junto a git, no en su lugar. Dos extras: /btw responde una duda rápida sin añadir nada al historial, y /rename con claude --resume retoma un trabajo de varios días.

ImplicaciónUn prompt nuevo que ya incluye lo aprendido casi siempre supera a una tercera corrección encima de dos fallidas.

Sin ti

Antes de dejar a Claude trabajando sola, responde cinco preguntas

Todo lo anterior pesa más cuando no estás para atrapar errores. Mientras miras, un contexto que falta se nota en uno o dos mensajes; en una ejecución que dejaste de noche, nadie lo dice y descubres a la mañana que construyó toda la noche sobre un supuesto equivocado. Antes de dejarla, la guía propone repasar estas cinco preguntas con esa tarea concreta en mente.

Para ejecuciones sin supervisión, claude -p "prompt" corre una vez y sale, y así llega Claude Code a CI, a git hooks y a bucles de shell. En un script casi siempre quieres --bare (que ignora hooks, skills, plugins, MCP y los CLAUDE.md para que la ejecución sea igual en cualquier sitio), herramientas pre-aprobadas con --allowedTools y --permission-mode dontAsk, que rechaza todo lo demás. La guía aconseja probarlo con tres archivos antes de lanzar el resto.

bashbucle con tope
$ for file in $(cat files.txt); do
    claude --bare \
      -p "Migrate $file to the new logger API and commit. Reply OK or FAIL." \
      --allowedTools "Read,Edit,Bash(git add *),Bash(git commit *)" \
      --permission-mode dontAsk \
      --max-turns 20
  done

Para empezar una ejecución, algo tiene que decidir cuándo: tú, un temporizador o un evento. /loop repite un prompt dentro de una sesión abierta; /schedule crea una tarea programada en la nube que corre aunque cierres el portátil, y antes de dejarla protege main con una regla de GitHub que la tarea no pueda saltarse. Para trabajar en paralelo, claude -w feature-auth abre una sesión en un worktree nuevo, y /batch parte un cambio mecánico grande en entre 5 y 30 unidades, cada una con su worktree y su PR. Y una segunda sesión es la manera más fácil de tener un revisor independiente: una escribe, otra revisa sin haberlo visto escribir.

ImplicaciónDe la tarea larga se encarga Claude. Lo que sigue siendo tuyo es lanzarla, decidir qué significa «hecho» esta vez y aprobar el merge al final.

Lo que ya no hace falta

Siete consejos que fueron buenos y los modelos actuales ya hicieron innecesarios

Casi todos eran apaños para algo que el modelo todavía no hacía bien. Si alguno sigue siendo una costumbre, esto explica por qué se puede dejar.

Gestiona el contexto de forma agresiva, es tu límiteLa mayoría de los modelos tiene 1M de tokens y compacta solos. /clear entre tareas sigue valiendo: un contexto enfocado da mejores respuestas y cuesta menos.

Límites

Lo que la guía no dice

  • Es documentación oficial y recomienda prácticas, pero no presenta mediciones: casi todo es «casi siempre», «suele» o «tiende a».
  • Los valores por defecto, el modelo y el nivel de esfuerzo que cita pertenecen al momento en que la consulté y pueden cambiar.
  • Algunas piezas se describen como en desarrollo, por ejemplo claude agents, que sigue en vista previa de investigación.
  • No da cifras de costo ni de ahorro para ninguna práctica; los costos se señalan de forma cualitativa.
  • Los consejos para un equipo entero están en otra página (configurar Claude Code para una organización) y aquí no se resumen.
